# BSV 上 USDC 储备支持型代币协议规格

版本 0.2 · 2026-11-25 · 评审稿

## 目标与范围

定义由源链 USDC 储备支持、在 BSV 发行的代币。首轮在测试网验证 入金 → 铸造 1,024 → 拆分 → 冻结及解冻 → 合并 → 销毁 → 释放。CCTP 用于受支持链之间的原生 USDC 调拨。BSV 段先用独立测试储备和证明适配器，正式环境以 Circle 确认的 xReserve 接口及责任为准。 [xReserve 工作流](https://developers.circle.com/xreserve/concepts/how-xreserve-works) · [xReserve 域清单](https://developers.circle.com/xreserve/references/supported-blockchains-and-domains) · [CCTP 域清单](https://developers.circle.com/cctp/concepts/supported-chains-and-domains)

下表是本项目要求。外部合作条件见文末。测试网使用独立域、资产和测试密钥。

## 三项协议判据

候选实现一律从以下判据验收。资产由收款人事先选定的网络、发行锚和策略标识。Script、Groth16、库存树、交易布局和证明聚合方式是设计选择。已入块的样例只能作为对应场景的证据，安全结论还需要独立审查协议关系、所有分支及实现。

1. **资金恒等。** 对同一资产的一笔状态转换，精确满足 `已认证输入之和 + 本笔合法净铸造 = 全部代币输出之和 + 本笔合法销毁`。普通支付的铸造量、销毁量均为零。逐槽读取经过认证的数量，防止遗漏、重复计数和溢出。费用与找零按所属资产入账，BSV 矿工费单独使用 satoshi。跨链账在同一确认口径核对净储备、待铸造、流通和待释放，每个事件最多结清一次。两侧确认有时间差时保留在途项。
2. **真伪溯源。** 收款人可以从自己收到的具体 `txid:vout` 验证，创建交易有权生成这个输出，实际消费的每枚代币均由合法前序输出派生，最终回到约定 Genesis 下的合法铸造。每一步均须认证适用的锁、策略、执行权限和真实交易。即使发行方同意为一份错误清单或普通付款签字，该签字也不赋予它代币价值。收款的链确认、双花及当前可用性依下节分别判定。
3. **可扩容。** 固定本笔输入输出形状时，铸造或转账的历史深度不得给链上交易、见证或为它专门创建的验证器交易增加字节。验证应能复用上一步已验证的结论；记录新收款人的同步、验证和再出证成本，检查是否把重走历史的代价转移到了钱包。固定历史再增加输入输出宽度，分别测异父、共父、同持有人、多持有人的全包字节、出证时间和峰值内存、节点及钱包成本。普通付款若依赖所有钱包争抢全局唯一的 UTXO，还需给出并发吞吐证据。64→64、256→256 是容量测试点，实际预算及验证结论单列。

比较两个候选时先对齐铸造信任边界、收款验证条件和可独立转付的权利，再比较完整费用和性能。固定形状允许固定的协议开销；签名或证明编码本身的长度波动应单列，并说明上界。两笔实测可揭示历史增长，百次转账的保证还需为所有合法深度给出序列化长度与验证关系上的依据。

审查全局供应时，可以从 Genesis 开始维护一张只含已授权、尚未消费代币输出的概念账表。每笔转换移除本笔真实消费的条目，将全部获授权后继按新 outpoint 加入。普通转账前后表内余额之和相同；铸造或销毁的唯一许可解释全部差额。用这张账表做验收判据，无须让实现或收款钱包实际保存全局账表。只有对全部准许动作和版本证明这个归纳步骤成立，才能将样例上的恒等推广到任意交易历史。

## P0 · 收款人独立验真

普通 BSV 收款的安全目标是，收款人凭预先认可的资产、Genesis outpoint、策略版本和验证密钥，使用自己的验证节点或能独立核验的材料，判断指定的 `txid:vout` 是否是付给自己的合法代币。即使付款人、出证服务和发行方共同认可一笔无合法来源的普通付款，收款钱包也必须拒绝。允许第三方提供证明、交易或区块位置，收款人自行验证。普通收款和后续普通转账均无须发行方在线、逐笔签字、批准库存根或补发专属票据。改变这个条件就改变了协议的信任模型。

| 收款人须确定的事实 | 主线验收条件 |
|---|---|
| 输入从何而来 | 从本笔每个实际代币 vin 取得真实父 `txid:vout`，独立验证前序结论与同一 Genesis、资产和策略相连。采用递归 Groth16 的实现还须认证验证密钥、公开声明和本次实际花费的关系。证明**该 vout** 正是父交易授权的代币槽，并从中读取可用状态和数量。基例必须从约定 Genesis 按策略核验一次性铸造授权。普通 BSV 输入贡献零代币。 |
| 该交易授权了哪个输出 | BSV Script 和经其验证的证明共同绑定实际输入、验证器、持有人授权和完整有序输出。每个输入恰计一次。普通转账只以已认证代币数量验守恒。钱包从创建交易独立定位收款 vout，核对认可的后继锁、约定收款公钥和六位整数应收金额。相同锁字节、同一父交易中的其他 vout、对任意清单的有效成员证明都不足以授权此输出。 |
| 此刻是否可用 | 在钱包采用的 BSV 链视图中验证包含和确认深度，另查该 outpoint 的未花费状态、已知冲突及适用的冻结或暂停规则。未知、确认不足、存在冲突或冻结时不得计入可用余额。按 outpoint 幂等记账，重组后重验。收款人日后正常花费已确认的币，应扣减余额并保留当时的付款记录。 |
| 收到后能否独立转付 | 收款时可获得或独立取得下一笔普通花费所需的数据、公共证明参数和可验证的来源材料。由接收钱包使用自己的签名器构造下一笔，允许自行出证或选择可替换的出证服务。正常网络费用及协议已生效的冻结政策适用。 |

递归保证的终点是**协议认可的合法铸造**。本项目现有桥以配置的储备 RPC、最终性策略和授权签发认证源链入金。BSV 上独立验真的范围包括按这套策略合法发行及此后的全部 BSV 转移；储备托管、源链观察和实际兑付各有独立的信任边界。[铸造和签发](mint.md) · [递归关系](recursive-provenance.md)

**安全验收先于体积比较。** 在同一测试发行锚，先做两笔连续普通转账。第二位付款人只消费上一笔付给自己的一个输出，可搭配自己已有的另一笔独立来源；发行签名器在两笔普通付款期间离线。收款钱包独立验指定 vout 并转付。负例包括有发行方签名但缺少 B2G 的清单、复制真实锁、合法父交易中的错误 vout、换验证密钥或验证器、证明与本笔错配、错收款人或金额、重复认款和确认块被撤销。先过上述门槛，再比较固定形状每代历史增量、验证脚本和全部专用资金的字节。

**当前证据。** v3 在独立 regtest 核对过 64 个不同直接父的递归连续性、Script 父绑定及付款首尾 vout。另一次两笔异父 `2→2` 在发行进程退出后，由接收方认证实际父输出并从链上恢复前序证明，完成独立转付。严格钱包接口核对订单和当前可用性，历史收据单独保留。两笔全包从 13,326,214 增至 26,608,881 字节，当前父原文布局未过零增长门槛。模板票据 I 的 247,545 字节依赖发行方批准的库存根，只计入脚本体积实验。三项判据还没有在同一实现中通过独立安全审查和容量验收。[两笔安全收款实测](secure-receipt.md) · [64 档入块记录](capacity.md) · [票据实验](inventory-payments.md)

v3 容量回执调用 `gettxout(txid, vout, false)`，记录该节点已确认 UTXO 集中的观测。收款钱包还需按其冲突策略查询节点已知的未确认花费，并在采用链变化时重新核验。[容量钱包调用](../recursion/run_capacity_regtest.py) · [BSV Node 的 UTXO 与 mempool 查询](https://github.com/bitcoin-sv/bitcoin-sv/blob/v1.2.3/src/rpc/blockchain.cpp#L1809-L1821)

## 对象与职责

| 对象 | 定义 |
|---|---|
| 储备适配器 | 认证源链域、原生 USDC 与储备合约、存款事件和释放结果。 |
| 证明服务 | 认证源链入金或已确认的 BSV 销毁，输出可验证并具有用途约束的证明。入金和赎回分别定义信任根。 |
| 持有人、收款人 | 持有人授权消费代币 UTXO。收款人可提交付款，并独立认证收到的指定输出及确认依据。 |
| BSV 节点 | 执行脚本和共享证明验证，按共识解决重复花费。 |
| 协议管理方 | 管理权限、冻结、暂停、版本和限额，记录每次变更。 |
| 资产描述符 | 包含协议版本、BSV 网络、资产 ID、发行锚点、精度、许可的源资产映射，以及锁模板或验证密钥标识。 |
| 代币状态 | 包含资产 ID、最小单位数量、持有人标识和活跃或冻结状态。satoshi 金额独立计算。 |
| 跨链记录 | 入金和销毁采用不同域分隔。规范化绑定源域和目的域、资产、事件标识或 nonce、金额、收款人、费用与版本。各签名和哈希有唯一的字节序及序列化规则。 |

## 协议要求与验收

| 编号 | 必须实现 | 验收条件 |
|---|---|---|
| R01 资产识别 | 认证描述符、网络及代币输出模板。数量使用有界整数，桥接换算精确，费用单列。 | 拒绝同名假资产、错域、仿造模板、越界金额和无法精确换算的金额。 |
| R02 入金认证 | 认证真实储备入金的域、合约、原生资产、事件位置与确认状态。铸造金额和收款人取自已认证字段。 | 错误合约、未达确认策略或已被重组撤销的入金不能取得新的铸造权。 |
| R03 一次性铸造 | 验证签发人、目的域、收款人、净数量及费用。原子消耗唯一入金权利和从 genesis 延续的当前铸造状态。新版状态强制累加实际净铸造量。 | 同一入金并发提交时最多铸造一次。换域、换收款人、增量、错钥、错发行锚、错误累计量和旧版本均拒绝。 [铸造状态](recursive-provenance.md#从-genesis-延续的铸造状态) |
| R04 普通转账 | 认证所有实际消费的代币 outpoint、合法发行或前序证明、持有人授权、金额守恒和实际后继输出。每笔 MIMO 可共享一次 Groth16 验证。 | 拆分、合并和多来源输入通过。超额输出、遗漏槽位、假父交易、重复输入、错误后继和旧证明重用均失败。 |
| R05 冻结和解冻 | 专用角色可变更指定 UTXO 状态。每个输入对应不同的后继输出，资产、数量、持有人和策略身份保持一致。试验默认先解冻再销毁。 | 冻结后禁止普通支付。错钥、改量、换持有人和重复后继失败。冻结与支付竞争同一 outpoint 时，以实际确认的花费为准。 |
| R06 暂停及地址政策 | 分开定义铸造暂停、释放暂停和适用的普通转账限制。若要求全局转账暂停或持续地址封锁，必须绑定实际生效的策略版本，定义状态争用及故障行为。 | 暂停期间对应操作被拒绝。启用地址政策后，旧名单证明不能授权被封锁的发送方或收款方。 |
| R07 销毁 | 绑定数量、目的域、收款人、费用和唯一赎回标识。部分销毁满足输入金额等于后继数量加销毁量。 | 全额及部分销毁通过。拒绝虚假销毁、错误找零、重复输入和篡改收款人。 |
| R08 源链释放 | 验证满足确认策略的合法销毁，以及证明签发范围。储备侧原子标记已结清。失败可对原赎回请求幂等重试。 | 一笔销毁最多释放一次。错域、错资产、错收款人、假销毁及确认不足均不释放。 |
| R09 储备与供应 | 按资产、储备域和币种精度对账，跟踪待铸造、流通余额、冻结余额、待释放和已释放。对账差异触发约定的暂停及处置。 | 流通量包含冻结余额。每项权利可追溯到资金事件，费用、退款和异常拨备用独立分录解释。 |
| R10 确认与恢复 | 定义两链确认、重组回退、事件补扫、幂等状态迁移和人工复核。明确已采取跨链动作后发生深重组时的处置。 | 重复投递、乱序、重启和故障恢复均不产生重复权利。 |
| R11 权限及升级 | 分开定义铸造、赎回证明、冻结、暂停、升级的角色和门槛。定义轮换、撤权、旧证明处理及存量 UTXO 迁移。 | 错钥和撤销后的授权失败，合法轮换和存量迁移保持资产身份与供应可核查。 |
| R12 钱包验收 | 识别具体收款 vout，验证其属于协议认可的创建交易，并验证 Merkle 包含和所采用的区块头确认。分别显示确认、冻结、赎回及已知花费状态。 | 给定付款材料，钱包能独立验证指定输出，拒绝错误 vout 及不匹配的模板。交易包含证明与当前未花费状态分别判定。 |
| R13 端到端证明 | 以合法铸造为基例，证明普通及行政转移、销毁和释放保持供应与储备不变量。使用真实交易绑定的代币电路，先通过独立 BSV regtest，再跑跨链测试网。 | 正例走完整生命周期。负例包括超发、双重赎回、替换验证器、冻结竞态、重组和证明服务恢复，并标出拒绝层。生产发布需要正式证明参数与独立审计。 |
| R14 容量和成本 | 用 64→64 和 256→256 记录准备及付款字节、每输入见证、出证和节点验证耗时、钱包验收成本。分别测共享前序与多笔前序。 | 产出可复现基准。正式容量、费用与延迟目标根据真实代币证明的实测设定。 |
| R15 运营管理后台 | 提供易操作的测试后台，查看两链事件、资产供应与储备差额、当前确认和暂停状态，并按权限发起铸造、冻结、解冻、暂停及释放请求。审批及外部签名与浏览器界面分离。 | 最终集成时通过已配置的 Wrangler 将测试后台部署到临时域名 `cctp.linzheming.com`。验收角色权限、确认及失败回显、同一事件重试、审计记录和防重复执行。 |

### USDC 数量和精度

USDC 储备与 BSV 对应代币固定使用六位小数。协议消息、脚本、证明和账本的数量、费用、找零采用无符号整数最小单位。1 USDC 等于 1,000,000 最小单位。一笔跨链义务的金额使用 uint64，BSV 中的 satoshi 独立计量。本项目验收样例的 1,024、640、384 均为最小单位，分别显示为 0.001024、0.000640、0.000384 USDC。

人输入的 USDC 金额用十进制字符串精确解析。可输入 0 至 6 位小数，超过精度、科学记数法、负数及超出 uint64 一律拒绝。显示层固定补足六位。JSON 和后台接口用字符串承载最小单位，避免 JavaScript 浮点数吞掉低位。铸造与释放校验资产描述符的精度与源链 USDC 一致。参考边界实现见 [usdc_amount.py](../reference/usdc_amount.py)。

### 对账不变量

在无费用、退款和拨备的测试模型中，归属于本协议的已确认净储备等于**待铸造金额 + 流通金额（含冻结） + 已销毁待释放金额**。已释放金额从净储备扣除。每笔存款或销毁在状态机中只有一个当前状态。

入金顺序为观察到、达到确认条件、取得铸造权、铸造已确认。赎回顺序为观察到销毁、达到确认条件、可释放、释放已确认。待确认与已确认分账，异常处理保留原事件标识。
