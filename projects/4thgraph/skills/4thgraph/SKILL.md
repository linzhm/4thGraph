# 4thGraph

Use 4thGraph to turn a Forth word into a Script fragment or a workflow into locking scripts and a symbolic transaction plan. Return the actual build outputs and explain the constraints that affected their compilation.

## Before you write Forth

- Confirm the required outputs and failure conditions, integer widths and overflow behavior, signing roles, and which inputs and signers can be available together. Identify any step one party must be able to submit independently.
- Read the project's pinned compiler version and capabilities first. Run `4thgraph --version`, `4thgraph --capabilities`, and `4thgraph --help`. Record the checkout revision when using repository tools. Revisions can share a version string, so check the specific words, flags, and entry points before using them. From the repository root, the equivalent compiler entry point is `PYTHONPATH=. python3 projects/4thgraph/protocol.py`. For setup, see `projects/4thgraph/INSTALL.md` in the [4thGraph checkout](https://github.com/linzhm/4thGraph).
- Choose the optimization objective and boundary cases before changing the source. Keep a baseline build for comparison, and record which conditions and rejection behavior every candidate must preserve.
- Use the supported subset of Forth 2012. Write the stack effect immediately after the definition name, as in `: name ( inputs -- outputs ) ... ;`. Read stack signatures from bottom to top, with the top item on the right. Define callees before callers. `( ... )` is a comment. Both arms of `IF ... ELSE ... THEN` must leave the same ordered stack types.
- Prefer small words that express the calculation directly. Use typed arithmetic and named intermediate values where the frontend supports them. Let the compiler schedule stack accesses before tuning `PICK` or `ROLL` by hand. Where supported, write counted repetition with literal bounds in Forth order, as in `256 0 ?DO step LOOP`. Use `I` for the innermost loop index and preserve the loop-carried stack types. Check the expanded cost of nested loops with preflight.
- Numeric literals are `cell`. Standard `+` uses 64-bit signed cell representation and wraps modulo 2⁶⁴ in 4thGraph. `u32+` wraps modulo 2³². Convert explicitly with `cell>u32` or `u32>cell`. Standard Forth comparisons return `-1` or `0`. Preserve the full flag when it is returned to a caller.
- For wider ScriptNum arithmetic, use `script-int` and explicit words such as `cell>int` and `int-rem`. Declare justified half-open bounds with `range: name base lower upper ;`. Use the default `--entry` checks for untrusted arguments and `check-range name` to validate a value inside a word. Use `--assume-input-ranges` only when the enclosing Script already validates the same bounds and canonical numeric encoding before calling the fragment. Identify that check in the build notes.
- Check optional words against `--capabilities` and load source dependencies with `REQUIRE filename`. Put UTXO lookup, external signing, and transaction submission in the host workflow. Write Script-bound definitions with supported words and static stack effects.

```forth
: inc-u32 ( u32 -- u32 ) 1 cell>u32 u32+ ;
```

## Declare transaction constraints

- For the supported two-branch workflow, use `work: step input word role ;` with `u32 -- u32`, and `join: step left right word ;` with `u32 u32 -- route`. Check the left/right order and the requested terminal route. Declare the split signer with `split-authority: role ;`. When a gate is needed, use `gate: step input word role ;` with `u32 -- cell`, where nonzero allows the workflow to continue. See `projects/4thgraph/syntax.md` in the checkout.
- Use `independent-submit: step ;` for a required transaction boundary. The availability flags describe which inputs and roles can participate together in this build. A repeated external input name declares the same value across uses and may require that value at an earlier step in a split plan. Check the emitted template's requirements and where data becomes public.
- Select `--mode fused`, `split`, or `auto` for transaction scheduling. Set `--target` separately for allowed transaction versions. For full-plan builds, supply the required roles' public keys and a 32-byte hexadecimal task ID. Leave signing to the external signer. Verify that the plan binds real parent outpoints, common split origin where applicable, and expected successor outputs when it is instantiated.
- If the source uses `recovery: height role ;`, trace which live outputs can be refunded and which normal spends conflict. For a refund with `nLockTime = h`, the earliest block is `h+1`. Use `recovery_replay.py` for the normal path, single-branch exit, early refund and competing spends. Report non-final pool admission, confirmation and conflicts separately.

## Compile and optimize

1. Compile a single word with `4thgraph source.fth --entry word`. Where `--preflight-only` is available, use it first to read expansion counts, loop locations and estimated bytes before lowering. Compare `--optimize baseline`, `safe` and `stack` as supported. `safe` uses range analysis and branch lowering. `stack` also schedules last uses and can share computations where their semantics permit it. Use the emitted byte count and any reported source-line costs for the final result. Inspect reported rewrites for their locations, conditions and byte deltas. The R1 window example at `projects/4thgraph/p2pkh-r1/window-ranges.fth` exercises remainder elimination with proven bounds. See the P2PKH-R1 documentation for the complete-lock build and replay.
2. Use compiler-reported costs and candidates to decide where to tune. A per-call saving can repeat at every inlined call site. Both Script branch arms contribute to the lock size, while execution counts and measured stack peaks depend on the test vector. Describe the winner in terms of the candidates the tool reports. Reserve hand-tuned assembly for a measured hotspot or an explicit opcode or byte-layout requirement. Recompile after changing a formula and compare against the saved baseline before introducing manual stack shuffles.
3. For Schnorr checkouts that provide `projects/p2pkh-schnorr/docs/4thgraph-cost.md`, follow that guide and use the project's pinned Python environment. Run `projects/p2pkh-schnorr/reference/generate_template.py --preflight-only --mode stack` to see the selected schedule before emission. Use `--max-script-bytes N` with preflight when there is a byte budget. Use `compare_forth.py` to compare `source` and `stack`, with `--previous` for a compatible saved report. Generate candidate templates in a separate output directory and check the field offsets, template hash and actual signing `scriptCode` against the final bytes.
4. Hold the source, target, key roles, and test data fixed when comparing optimizations. Compare Script and whole-path bytes, peak main and alternate stack payload, and measured validation cost where available. Compare settlement and review separately and preserve the exclusion reasons for ineligible candidates. Let the toolchain enforce candidate validity, budgets and ranking.
5. Check results and rejection behavior on the relevant boundaries, including wraparound, range endpoints and noncanonical encodings, both terminal routes, and any independent-submit constraint. For transaction changes, include applicable cases for missing inputs, wrong parent outpoints, unrelated split origins, and wrong successor outputs. Use the checkout's regtest workflow for BSV Node and pinned chain-gang evidence.

## Choose a layout for expensive computation

Use preflight or the compiled baseline to identify which computation or expanded history dominates the cost. Define the relation that must hold and the required transaction behavior before choosing a layout. Specify the input state, valid successor, authorization, commitment to the actual spend, and which steps must succeed atomically. For history checks, specify the authenticated starting point and how the required predecessor links are verified.

- **Direct Script.** Keep direct verification as a baseline where eligible. Check deployment and spend bytes, peak stack payload, and validation cost using the same inputs and target.
- **Split transactions.** Declare the stages and the state their intermediate outputs carry. Use `--search --explain` to compare supported fused and split layouts. Where available, use `--max-tx-bytes` with search for a per-transaction budget. `path-bytes` ranks by estimated path size. `peak-validation` starts with signature checks and input script bytes. Check the true parent outpoints, independent authorization, and recovery when a later stage stalls. Compare the largest transaction and the entire path, including intermediate witnesses, fees, and confirmation dependencies.
- **Proof-backed verification.** Express the supported computation as a `relation:` and use `4thgraph-verify` or `verification.py` to compare the available backends. Enable `--r1cs` or `--groth16 ZKEY PHASE2_PTAU` where supported. Use `--policy allow-direct` when direct verification is permitted. Apply `--max-lock-bytes` for a lock budget and set `--objective path-bytes` or `lock-bytes`. Check the public-input binding to the actual outpoint and successor. Compare verifier lock, proof witness, full transaction bytes, and off-chain proving cost. Transparent R1CS discloses the assignment. For Groth16, verify that the setup matches the circuit and record which inputs are public.

Transaction layout determines how the work is staged. The verification backend determines how each supported relation is checked. A split workflow can use a proof-backed stage when the toolchain can bind that proof to the stage's actual input and output. Count a candidate only when its generated contracts enforce the declared relation, state continuity, and authorization. Read [circuits and verifiers](references/circuits-and-verifiers.md) for backend setup, public-input encoding, and replay.

## Use the CPN transaction plan

- Export the selected workflow with `--cpn-plan` and retain the build's `plan_sha256`. Use `--cpn` to render the same canonical plan for review. For a fused or split candidate, check ordered input and output slots, state carried by intermediate UTXOs, authorizers, field constraints and recovery transitions. See `projects/4thgraph/cpn.md` where present.
- Use the plan with real outpoints, available witnesses and signers, and the next block height. Check which transactions are enabled, which need a predecessor, and which spend the same UTXO. Use plan-aware signing to check the draft before calling a signer. Where available, use `graph_replay.py` and `cpn_replay.py` with the supported fixtures to check confirmed state changes, independent step ordering and refund conflicts against the recorded engine verdicts.
- Workflow layout search ranks eligible candidates by its static cost objective. Verify availability, state continuity and recovery on the exercised paths with the checkout's replay tools. For a single `relation:`, use the `4thgraph-verify` report to compare Script and proof backends.

## Deliver the result

Provide the source and the compiler's JSON or Script fragment, together with the chosen mode, target, and optimization. For a workflow, include the build digest and the reason for transaction boundaries. Use `4thgraph-report replay.json --output-dir decision` to check saved evidence against build digests and report which paths were replayed. From the checkout root, use `PYTHONPATH=. python3 projects/4thgraph/decision_report.py` with the same arguments. An offline compile establishes the build result and static eligibility. Label actual replay coverage separately.
