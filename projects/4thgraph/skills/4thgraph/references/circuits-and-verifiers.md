# Circuits and verifiers

Use the tools and examples from the pinned BSV Script Lab checkout. Check the selected entry point and its `--help` before building. The installed `4thgraph-circuit` and `4thgraph-verify` commands can build outside the checkout. Use the checkout for funded replay.

## Forth to circuit

- Use `projects/4thgraph/circuit_backend.py` with `projects/4thgraph/proof/workflow.fth` as the authoring example. Keep the entry effects `advance ( u32 -- u32 )` and `decide ( u32 -- route )`. Use the circuit subset documented in `projects/4thgraph/language.md`. Verify wraparound and branch thresholds in the host, Script and circuit.
- Use `proof_replay.py --generated --compare-domains` with the project's regtest launcher to check the generated circuit and the transparent R1CS verifier. This verifier checks a disclosed full assignment. Its example derives the public binding from the authenticated full ForkID ALL preimage and checks the actual successor output.
- For a `relation:` declaration, use `4thgraph-verify` or `verification.py` to compile the same resolved words to Script and Circom. Report the eligible paths after proof policy, setup and lock-budget checks. Use the generated R1CS path to bind the circuit to the verifier.

## Groth16

- Check which curve and public-signal order the existing verification key and proof use. Use the checkout's verifier for that curve. The prover runs off-chain. Keep test-only keys and setup material confined to test fixtures.
- For BN254, look for `projects/4thgraph/groth16_script.py` and `groth16_replay.py`. This path takes a pinned Rúnar checkout, a verification key, five fixed public signals and an owner key. It uses Chronicle opcodes. The owner authorizes the actual spend with a ForkID ALL signature.
- For BLS12-381, prefer `projects/4thgraph/groth16-bls12-381/build_verifier.py` with `verifier.fth` when present. Earlier revisions expose `groth16_bls12381.py`. Follow the checked-out verifier README for dependencies and matching fixtures. Match `--input-sources` to the verification key's slot order. A scalar fixes a slot at deployment, `null` permits the full Fr range, and `{"bits":128}` permits a bounded unsigned value. Use `{"max":"…"}` for an inclusive bound when the entry point supports it. The full `--public` statement is used for optional witness generation.
- If supported, use `--objective path-bytes`, `lock-bytes` or `witness-bytes` to compare verifier layouts under one statement and input configuration. `path-bytes` scores the serialized lock and proof witness fields for one deployment and spend. Measure the full transaction separately with its application data and signatures. Use `--witness-layout` to match an existing witness encoding. `--script-era` controls available opcodes. Chronicle-specific locks require an output created after activation. Verify the transaction version and application sighash independently.
- Decide what the public statement must commit to and where the lock checks it. For a transaction-bound application, authenticate the relevant outpoint, outputs and any required amounts, then derive or check the same public input bytes passed to the verifier. Owner authorization and proof-to-transaction binding are separate checks. For CCTP, follow `projects/4thgraph/cctp/README.md` where present and use the preimage format demonstrated by that checkout. A Chronicle opcode build alone leaves the application's sighash format unchanged.
- Replay the exact lock and witness with the supported engine settings. Include an accepted proof, changed proof data, a proof for a different statement, and wrong outputs or spend context if binding is required. Exercise malformed statements and out-of-range dynamic inputs where applicable. Record the source, verification key and lock digests, curve, era, input slots and layout. Compare lock, witness and full path bytes, alongside stack peaks and actual verification time when measured.
