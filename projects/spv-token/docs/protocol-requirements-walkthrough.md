## 一、从收款人的目标看协议

商户约定收款地址和金额后，需要能回答四个问题。这个具体输出是否来自认可的发行锚？数量和收款公钥是否正确？它在自己采用的链上得到几次确认，目前是否可用？只拿到这笔收款和普通 BSV 后，自己能否付给下一位？前两问关系到真伪和供应，后两问关系到款项能否入账和使用。普通付款须允许持有人独立签名、选择出证者、自己准备验证器资金。跨链的入金签发、依法授权的管理动作和储备释放有各自的授权边界。[P0 收款要求](../README.md#design-conditions)

当前证据最完整的是固定两个业务槽的 双槽生命周期。本次从原始交易重放了九笔已入块动作，并从每笔实际花费的 outpoint 和实际输出重算了流通余额。它实现了双槽收款、转付、两种管理状态和赎回。**最影响付款产品的缺口是单币转付**。普通付款要求两枚可用代币输入、两个正数代币输出。只收到一枚的用户仍需要另一枚合法代币才能付款，或者需要引入另一位持有人协作。固定两个物理槽节省了验证和计量上的不确定性，也把这种限制写进了电路。[交易线格式](../recursion/prepared_lifecycle_wire.py) · [双槽生命周期 生命周期与验收](two-slot-lifecycle.md)

## 二、一笔支付由哪些交易和证据组成

| 部位 | 谁提供 | 实际约束 |
| --- | --- | --- |
| 两笔准备交易 | 任何有普通 BSV 的付款人或赞助人 | 分别创建伴随输出和含完整验证器的输出。锁和资金形状由策略规定，可重新出资。每笔结算花自己的两枚准备 UTXO，普通支付无需争用发行锚。 |
| 结算 `vin 0` | 花费伴随输出 | 通过节点验签绑定本笔交易的有序 prevouts，核对 `vin 1` 真实花费的资金交易哈希、`vout 0` 和完整验证器锁的承诺。付款人有权出资，策略控制它必须运行哪段验证代码。 |
| 结算 `vin 1` | 花费共享验证器输出 | 在 `0x41` ForkID ALL 上下文核对实际输入向量、本输入位置和全部输出哈希。从有序 prevouts 取出两个业务 outpoint，重建声明摘要的两个公开输入，验证一份普通 BLS12-381 Groth16，再用 Script 对同一交易核验两个角色签名。归档参数的 BSB22 承诺数为零。 |
| 结算 `vin 2,3` | 普通付款提供两枚代币，铸造提供发行锚或发行状态加普通费用币 | 每个协议状态锁要求本笔实际消费策略指定的伴随锁。由此把持币输入、伴随输入、验证器输入连成一次强制执行。普通付款的角色公钥由电路从真实父输出读取，持有人原生验签集中在 `vin 1`。 |
| 结算 `vout 0,1,2,3` | 验证器约束钱包生成的输出 | 前两槽按动作分别承载发行状态、可用币、冻结币或不可花费空槽。后两槽承载销毁回执和入金事件记录，未使用时有规范占位。Script 重建四个完整 TxOut，与整笔实际有序输出承诺比较，覆盖 satoshi、脚本和次序。 |

**守恒在当前生命周期电路内。** 电路先从认证过的父输出读取数量及状态，再按动作检查 `输入代币 + 合法铸造 = 所有代币输出 + 合法销毁`。发行状态里的累计发行值另行更新，普通 BSV 费用输入贡献零代币。Script 把这条等式里的后继绑定到实际输出。较早的 双槽生命周期 普通付款版和 v3 将加法放在 Script，两版实验的职责分配不同。[当前结算与证明接口](../recursion/prepared_lifecycle.py) · [直接父元数据重建](../recursion/settlement_checkpoint.py) · [持币和伴随锁的实际资金校验](../../groth16/reference/transfer.py) · [测试参数](../fixtures/two-slot-lifecycle-regtest/parameters.json)

**溯源到 Genesis 的依据是逐笔强制执行。** 对本次选中的每个父槽，Script 从规定字段重建父前缀、SHA-256 中间态和已处理长度。电路从该状态续算固定后缀，核对与实际 vin 相同的父 txid、规范输出位置、所选 vout 的完整代币模板、状态和父交易实际消费的同策略伴随输出。合法铸造提供起点。只要每个被承认的父输出都由上述规则授权，且采用链上的前序花费均按对应规则有效，后继可沿这个性质归纳到发行锚。此处的 Groth16 证明直接父与本笔规则，前序规则的执行由 BSV 链承接。v3 则在电路内验前序证明，同时在 Script 里打开父交易。两种途径对历史字节和信任前提的影响不同。[父检查点与接续](two-slot-lifecycle.md#历史长度与钱包) · [v3 前序证明及钱包复验](two-slot-lifecycle.md#历史长度与钱包)

**桥的信任止于授权者。** BSV 验证的是符合发行策略的签名与状态推进。真实入金属于最终源链，由储备观察及铸造签发方认证。EVM 接受释放签发人对 BSV 销毁的认证。失陷的铸造授权者可能让没有相应储备的发行得到签名，失陷的释放授权者可能为错误兑付签名。一次性状态和结清键分别防止重用同一权利。独立归档重放、角色隔离和对账可以检查这些边界。当前测试储备为项目自己的合约，正式 Circle 接口和运营责任属于另行确认的合作条件。[桥的信任边界](../evm/public_testnet.py) · [原规格 X01–X04](../README.md#design-conditions) · [Circle 的 xReserve 工作流](https://developers.circle.com/xreserve/concepts/how-xreserve-works)

## 四、无索引收款与独立转付的边界

钱包从自己的配置取得网络、发行锚、资产、角色和获准的验证器。付款人可交付结算交易、实际直接父交易和各自的区块包含路径。钱包核对采用的头链与确认深度、每个真实 outpoint、创建交易执行的伴随锁与验证器、全体输入的 Script，以及订单要求的输出金额、公钥和状态。对代币收款还检查该笔定稿序列化能作为下一笔的直接父。归档的两笔异父付款，钱包各处理 1,098,551 B 交易加 160 B Merkle 分支，已有头链另计。收款人无需建立全链代币索引。来源材料仍需有人交付，独立验证与取得材料是两项成本。[收款实现](../reference/spv_payment.py) · [收款包计量](../recursion/spv_regtest.py) · [原始付款明细](../fixtures/two-slot-lifecycle-regtest/summary.json)

**历史收据、当前可用与独立转付有三个不同的验收结果。**

- 历史收据可离线验证。归档九笔各有两个确认，Bob 后续支付确实消费自己收到的 vout。钱包采用的是 regtest 专用头链规则。
- 双槽生命周期 的收款接口返回 `spend_status=UNKNOWN`。创建交易的包含证明无法告知它后来是否已被花费。可用余额还需要钱包自验的链状态及已知冲突、冻结检查、按 outpoint 幂等记账和撤块回退。[SPV 接口](../reference/spv_payment.py) · [SPV 包含证明的含义](https://developer.bitcoin.org/devguide/operating_modes.html#simplified-payment-verification-spv)
- 普通转付已证明持有人可以自己签名、准备验证器并选择出证者。双槽关系另外要求第二枚实际代币。单币钱包支付、单币冻结、单币赎回和全额普通支付到唯一收款输出，是常见用户场景。它们应当在基础协议的产品验收中单列。即使物理布局保留两槽，也需要为业务空槽及普通费用输入给出可认证、零贡献的分支。[当前结算关系](../recursion/prepared_lifecycle.py) · [本次用到的入金、费用输入与付款](../recursion/run_prepared_lifecycle_regtest.py)

本次用 Python 对原生命周期的 13,787,986 条约束做了三个普通支付实验。三例均用同一归档策略、真实父交易和 Alice 的角色公钥，经 `Policy.opening`、`Policy.statement`、`lifecycle_witness` 交给 `R1CS.solve`。费用币取自 `mint-200` 实际消费的普通 P2PK 父输出。在高度 112，它与第一次铸造所得的 300 同时存在。表中时间为见证求解或发现约束失败的耗时。[归档交易及高度](../fixtures/two-slot-lifecycle-regtest/summary.json) · [Python 见证入口](../recursion/prepared_lifecycle_prover.py)

| 支付语义 | 真实来源与后继 | 本次求解结果 |
| --- | --- | --- |
| 两枚币，正常找零 | 两笔铸造的 `vout 1`，300 + 200 → Bob 275、Alice 225 | 通过，25.83 秒 |
| 一枚币，普通 BSV 补齐物理输入 | 铸造 300 + 普通费用币 → Bob 275、Alice 25 | 约束第 13,405,386 行拒绝，21.54 秒 |
| 两枚币，全额付给单一输出 | 同一对铸造输入 300 + 200 → Bob 500、规范空槽 | 约束第 13,405,390 行拒绝，21.58 秒 |

把 500 拆成两个正额输出都付给 Bob，可表达同一总额，Bob 会收到两枚 UTXO。拆分要求数量至少为两个最小单位，付款人仍须提供第二个真实输入。
