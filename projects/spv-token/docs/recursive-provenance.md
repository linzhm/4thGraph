# CCTP 递归来源与铸造状态

## 递归的声明

CCTP 的代币依赖图允许拆分和合并。按照证明携带数据（PCD）的做法，每笔交易验证直接前序证明和本次规则，得出其后继输出同样从发行锚合法派生。Mina 给出在递归证明中维护状态转换的实例。Nova 的增量可验证计算适合参考如何处理单条连续的 SHA-256 带状态计算。BSV 的定稿 txid、实际输入身份和铸造权限仍需由 CCTP 明确绑定。 [PCD](https://cs-people.bu.edu/tromer/papers/pcd.pdf) · [Mina 白皮书](https://minaprotocol.com/wp-content/uploads/technicalWhitepaper.pdf) · [Nova](https://eprint.iacr.org/2021/370)

| 模块 | 必须认证的事实 |
|---|---|
| BSV 当前交易 | 本笔实际执行的输入、按 vin 和 vout 顺序排列的字段、真实花费、角色授权及当前执行的锁。新试验可使用 Chronicle `0x61`。需要比对前序聪数时，从实际 TxOut 认证取得。 |
| CCTP 递归证明 | 在相同发行锚和策略下，当前每个实际 Token 或铸造状态输入对应合法的直接父输出。验证父的有效 B2G 声明，并检查本笔动作、数量和输出满足规则。 |
| 两链观察与签发 | 源链规范入金、最终性、合约和资产身份仍由现有 RPC 与授权签发路径认证。赎回侧独立确认 BSV 销毁及储备结清。 |

当前连续性电路已经验证前序证明，父交易原文由 Script 用于确立前序证明对应的实际 `txid:vout`。首选目标是让新的递归电路把直接父认证和前序验证纳入同一份本笔证明。保留现有连续性密钥的过渡方案使用额外的独立父证明，先验证定长接口和成本。改变现有递归关系需要新电路、参数和策略版本。 [现有连续性关系](../recursion/continuity/circuit.go) · [父绑定构件](parent-binding.md)

新的一份证明同时验证父绑定、守恒和 B2G。以本笔已认证的完整 vin 向量分配输入槽，每个实际输入恰好分类一次，拒绝重复的 outpoint。每个代币槽从同一份父交易取得前序声明和精确 `txid:vout` 的状态。前序声明必须认证同一发行锚、资产和策略，并明确授权这个 vout 为可转账代币。守恒直接取该 TxOut 的数量。经策略识别的普通 BSV 费用输入贡献零代币。脚本中的代币标识只用于解析，确认余额还需有效来源证明。 [2→2 守恒约束](../recursion/conservation/circuit.go)

本笔证明也覆盖完整的有序 TxOut 向量，按动作规定的角色和精确锁区分代币、找零、回执等输出。全部获授权代币后继参与求和，后续证明从本笔已认证的上下文和规则恢复获授权的 vout。求和使用 uint64 代币最小单位，并独立核对聪数。当前 R1CS 测试组合了父交易 SHA256d、vout、完整输入与输出向量承诺及守恒。测试中的费用 outpoint 和锁后缀固定，正式电路仍需接入对父声明、发行锚、动作和策略的验证。 [父输出绑定](../recursion/parentcheckpoint/fixed_parent.go) · [组合约束测试](../recursion/conservation/bound_conservation_test.go)

本笔证明的公开声明包含资产、发行锚、策略版本、获准的验证密钥身份、动作及本笔交易上下文承诺。上下文承诺固定序列化的实际输入 outpoint、序列、输出、版本和锁定时间。若回执只记录前序摘要，它可纳入完整输出承诺。若设计让本笔回执携带本笔证明的声明摘要，摘要范围须排除该回执，并由 Script 对完整已认证输出验证回执的确定性构造。当前证明生成后才填完 `scriptSig` 并计算本笔 txid。后继证明可使用已定稿的直接父 txid。 [BSV 签名预像](https://github.com/bitcoin-sv/bitcoin-sv/blob/v1.2.3/src/script/interpreter.cpp#L1725-L1786) · [BSV txid 计算](https://github.com/bitcoin-sv/bitcoin-sv/blob/v1.2.3/src/primitives/transaction.cpp#L61-L74)

对本笔每个实际代币槽，递归关系从父原文重算 txid，解析真实 vout 和金额、锁及代币状态，再从同一父原文重建其前序声明。如果前序规则由 BSV Script 执行，还要认证父实际 verifier vin 花费了策略认可的资金输出，或以等价机制从策略认证该 outpoint。单独重验一份零前序递归证明无法认定铸造基例。策略身份必须绑定允许的验证密钥和状态模板，生成顺序须避免把随后才确定的锁哈希放回该锁的构造输入。 [铸造状态的 Script 基例](../recursion/issuance_base.py) · [现有密钥承诺](../recursion/keycommit)

父交易内的 `scriptSig` 由真实 txid 覆盖。后继证明可以把定稿父原文作为私有见证，在同一个递归电路内重算完整 txid，并对同一份字节解析选定输出及前序声明。链上只需要本笔证明和固定槽位。先用新交易形状测直接出证成本。SHA-256 分段是直接出证超预算时的链下优化，不是 B2G 的协议要求。采用分段优化时，各段须核对起始 IV、段序号与状态、交易字段、规范 CompactSize、总长度和填充以及第二重 SHA-256。现有叶证据只覆盖分段转换与固定位置字段。 [私有分段实测](../recursion/parentbinding/README.md#隐藏段数据)

## CAT20 的链上回溯对照

原 CAT20 在代币输入核对父交易及其某个实际输入，再打开该输入指向的祖父输出。开口要对应本资产的固定代币锁或专用铸造锁。合法前序花费执行同一条约束，因此节点可以逐笔维持从发行锚到代币输出的有效性。共享 Transfer Guard 以当前实际输入槽的状态为准求和，重建全部有序输出并核对 `hashOutputs`。代币输入验证所选 Guard 是实际花费的 UTXO、锁符合策略且本槽数量一致。准备 Guard 的交易和实际支付可以分开。收款钱包须在接收时核对所收输出的创建规则和真伪，脚本外观与区块包含只能提供待核对的候选。 [原版 CAT20 回溯](https://github.com/CATProtocol/cat-token-box/blob/8d5aeee7484bacc33d0014b44503c0b59d39aaff/packages/sdk/src/contracts/utils/backtrace.ts#L57-L90) · [代币与守卫的绑定](https://github.com/CATProtocol/cat-token-box/blob/8d5aeee7484bacc33d0014b44503c0b59d39aaff/packages/sdk/src/contracts/token/cat20.ts#L154-L172) · [守恒](https://github.com/CATProtocol/cat-token-box/blob/8d5aeee7484bacc33d0014b44503c0b59d39aaff/packages/sdk/src/contracts/token/transferGuard.ts#L74-L123)

原版参考实现使用 Taproot。签名和合约开口在 witness 内，计算 txid 时只序列化基础交易。OPCAT 链另外定义了 TxHashPreimage，交易哈希的预像把每个解锁脚本、后继锁和输出状态数据放入独立的 32 字节哈希。其签名预像还承诺实际消费的钱数、锁和状态哈希向量。BSV Chronicle 能认证当前交易的签名预像，BSV 的 txid 仍覆盖每个定稿 `scriptSig`。把 CAT 的两代回溯直接编码成 BSV 父原文会让每笔父原文嵌有更早数据。对齐后的 SHA-256 检查点可以缩短披露，后继要另外认证真实前缀、字段边界和输出位置。 [BIP141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki#transaction-id) · [OPCAT 交易哈希与签名预像](https://docs.opcatlabs.io/overview/key-differences/) · [BSV 父交易对齐实测](secure-receipt.md#父交易的输出边界对齐)

BSV 对照路线可以由 Script 维持递归 covenant。首次铸造固定实际发行 outpoint，后续铸造沿唯一铸造状态 UTXO 更新入金事件根及总量。每个实际代币输入把父交易与授权的祖父输出绑定到同一资产和策略，真实 Guard 集中核对本资产输入及全部后继。若金额和持有人编码在代币锁内，须按规范模板验证锁和状态，核对稳定策略身份。普通转账以六位整数最小单位求和，铸造和销毁分别核对明确的新增和扣减。设计中可用独立 SNARK 或 STARK 认证需要的难打开字段，再由各代真实执行的 Script 维持 B2G。该路线仍需在 BSV 实测小型父认证、Guard 绑定负例、独立收款、实际再哈希与零历史增长。 [父开口的同输入基准](../recursion/parentbinding/risczero/benchmark/README.md)

用于替代 SegWit 披露优势的公开证明需要绑定父 `txid:vout`、被选 TxOut 的序列化哈希、父内实际来源 vin 及其 outpoint、该 outpoint 对应的前一代 TxOut 哈希，以及资产策略身份。证明使用包含全部解锁字节的实际父或祖父原文，从共识 SHA256d 得到真实 txid，按规范编码读取 vin 和 vout。认证过的中间态可以分段复用。签名预像、对齐后缀或自定义的简化交易哈希可以参与声明，实际输入身份仍由共识 outpoint 确定。

父子交易布局下，付款人可以独立创建 Guard 或验证器资金，定稿后取得其 outpoint。付款子交易共同消费该 outpoint 和代币。Guard 将实际输入及输出承诺与证明绑定后才通过。定稿后的父证明可由收款人或公开证明服务预计算，以实际 outpoint、策略和证明程序身份作缓存键。这样可以把父 SHA-256 的出证时间移出付款等待，仍需计入前置时间和父子全包字节。采用原生递归 covenant 时，只有父级字段开口进入证明。采用递归证明时，同一组开口进入本笔 B2G 电路。分别测试两笔独立父的 `2→2`，再测 64 个独立父的付款，比较冷启动、缓存未命中、热路径和聚合的等待时间。

固定形状试验已确认两笔连续异父 `2→2`，付款各 4,075 字节，两笔含共享验证器资金合计 913,547 字节。两台隔离节点核对收款和实际再支付。Groth16 与 RISC Zero 对同一对实际父交易声明完成出证对照。 [真实付款、出证及守恒验收](covenant-backtrace.md)

## 从 genesis 延续的铸造状态

资产固定一个发行锚 outpoint。Genesis 消费这个锚，在 `vout 0` 创建唯一的初始铸造状态。之后每次铸造的 `vin 0` 消费上一笔实际状态输出，并在 `vout 0` 创建下一状态。直接消费 genesis 的输出最多发生一次。所有后续状态的证明回指同一发行锚。

新版固定长度状态字段如下。铸造事件 ID 和事件树沿用现有规则。

```text
MintState = (asset, policyVersion, eventRoot, cumulativeMinted, paused)
Genesis   = (asset, policyVersion, EMPTY_ROOT, 0, false)
```

- **铸造**由实际状态锁核验授权、入金用途和未使用事件。事件叶由未使用变为已消费。状态恰好生成一个对应的后继，`cumulativeMinted` 更新为上一个值加上本笔实际铸给持有人的净数量。每笔数量仍为六位小数的 uint64 最小单位，累计量建议使用固定 16 字节的无符号整数，并拒绝溢出。
- **暂停和恢复**走同一铸造状态链，只有授权角色可以改暂停位，继续携带原事件根与累计量。零前序只适用于实际消费未转移过的 genesis 状态。若先完成暂停和恢复，首笔实际铸造已经有状态前序。
- **普通转账**从实际 Token 父 `txid:vout` 继承发行来源，使用相同的固定 Token 证据槽位。铸造状态与入金记录属于铸造父交易的私有解析数据。普通转账无需消费最新铸造状态。
- **累计量**可以从同一状态链的最新有效输出核对。流通量还需扣除已确认销毁。升级同一资产时，授权迁移必须继承事件根与累计量，并将后继版本绑定到实际消费的旧状态，防止已用入金重新获得铸造权。

新版铸造与转账共用实际交易认证、规范父解析、`txid:vout` 绑定和同密钥前序验证。铸造分支把实际 `vin 0` 绑定到父 `vout 0`，按状态锁解析事件根、累计量和暂停位。这个分支核对本笔唯一获授权的代币输出等于入金净量，并延续一个状态输出。转账分支用同一父绑定构件读取获授权的代币 vout，再核对总量守恒。源链事件身份、最终性和签发仍沿用现有桥接口。

首次铸造核对父 genesis 实际消费本资产发行锚，且选定状态为空事件根、零累计量、未暂停。后续铸造用同一验证密钥核对实际状态父的前序证明。空槽和活动槽采用定长回执编码。前序状态交易原文、其证明和验证器资金原文留在链下证明器。链上保留本笔证明与固定布局的本笔字段。无论已消费多少位点，铸造状态始终只携带一个 32 字节事件根和一个 16 字节累计量。若沿用现有稀疏树，路径是固定 8,192 字节，可保留在实际状态输入或在联合电路里私下验证。

现有铸造锁已经串行继承事件根并阻止一次入金重复铸造。累计净铸造量是新状态字段，须由新版锁强制更新。这个串行 UTXO 会让不同入金的铸造竞争同一个当前状态，失败一方可按新状态重建。普通 Token 转账保持独立。 [现有铸造状态](mint.md) · [现有锁实现](../reference/mint.py)

## 首轮验收

同一测试发行锚确认两笔认证铸造，验证第二笔实际消费第一笔的状态。在普通付款前准备好两个钱包已有的独立代币来源。第一位付款人用两个实际代币输入做 `2→2`。收款人独立验真自己收到的一枚，搭配自己此前持有的一枚异父代币再做 `2→2`。两次普通付款期间发行签名器离线，且代币锁和验证器供给路径均不得要求逐笔或预签的发行方许可。收款人可从不同的证明服务或本地取得可验证材料。另保留两个同父后继共同花费的对照。每槽独立认证实际 vout。两笔普通转账须各自入块，取真实序列化及全部专用资金记录。固定形状历史增量为零，同时记录定长槽位、签名编码、证明次数、出证耗时和峰值内存。另测重复使用入金、伪造累计量、错误发行锚和策略、错父 vout、复制回执、替换实际验证器及现有冻结规则。[收款安全门槛](bsv-usdc-bridge-spec.md#p0--收款人独立验真)

铸造也须单独通过零历史增长验收。同一锚连续确认三笔认证铸造，首笔检查 genesis 基例，后两笔走同一继续发行分支。三笔共用固定链上槽位，以及与转账相同的证明电路、密钥和证明编码。逐笔核对实际状态 outpoint、累计净量与事件根，记录每个 `scriptSig`、证明编码、输出和验证器资金字节。要求祖先及其资金原文在每笔见证中占零字节，固定形状在统一签名编码口径下每推进一代增加零字节。

共用验证密钥的首轮电路须同时识别铸造和转账的父布局。铸造状态链消费父 `vout 0`，铸造产生的代币位于 `vout 1`。转账按实际动作确定可花费的 Token 输出位置。若用定长父布局降低 SHA-256 出证成本，先验证实际序列化。签名、证明字段和任何填充必须进入最终交易字节。较短的父交易按其真实长度执行 SHA-256 填充。固定形状的链上大小比较还须固定或单列签名编码的变动。

多布局父开口现在从同一个私有缓冲区按选定真实长度计算一次 SHA256d。未使用字节必须为零，实际 txid 不含缓冲区尾部。布局分支认证实际可选 vout 和规范输出边界，并从同一份输入、输出和最后一个完整 TxOut 重建 Chronicle 前序声明。验证器 vin 必须匹配同一资产策略已经认证的 outpoint。组合测试把两份重建摘要送入现有 BLS12-381 递归验签，拒绝用同一密钥下另一笔父交易的有效证明替换。测试前序使用小型测试电路出证，联合发行规则和独立节点验收仍待完成。 [组合测试](../recursion/continuity/parent_recursion_test.go)

现有 v3 连续性密钥已配合 v2 计数状态在独立节点通过同锚的两笔认证铸造和后继 2→2、1→2。原生 v2 计数锁也已在独立节点走完两笔铸造与中间的暂停和恢复，节点拒绝篡改累计量。SHA-256 字段叶已完成原生出证并拒绝把真实哈希状态和另一笔交易的输出字段拼接。联合证明和两笔定长转账的入块仍需实测。 [v3 计数连续性节点记录](../fixtures/v3-counted-continuity-regtest-summary.json) · [v2 计数节点记录](../fixtures/v2-counted-mint-regtest-summary.json) · [字段叶实测](../recursion/parentbinding/README.md#从分段打开固定位置的字段)

## 四输出的转账形状

新版回执使用独立域和版本，向链上写入前序数量及一个 32 字节承诺。承诺覆盖按实际 vin 排序的最多四个前序摘要及未用槽的零填充。序列化 TxOut 固定 77 字节，后继可从父原文恢复前序公开声明。每个代币 vin 继续独立绑定实际 `txid:vout`。回执无需携带前序列表或前序原文。

下表为当前字段的序列化模型。每笔有一个 verifier vin 和一份 1,862 字节证明见证。持币输入用 `0x41`，Token 锁按已有 1,546 字节、签名含类型字节按 71 字节数据计算。无协同输入，见证内无父原文和验证器资金原文。计算采用小于 253 个输入和输出的规范编码。最后一列只用现有 969,674 字节验证器资金作为参考，实际新锁大小须另测。

| 转账形状 | Token 父槽 | 验证器 `0x41` | 验证器 `0x61` | `0x61` 加参考资金 |
|---|---:|---:|---:|---:|
| 2→2 | 2 | 12,473 B | 12,341 B | 982,015 B |
| 1→4 | 1 | 16,693 B | 16,557 B | 986,231 B |
| 4→4 | 4 | 22,929 B | 22,807 B | 992,481 B |

模型中整笔大小为 10 字节交易框架、每个输入 43 字节框架、有序输出及各输入见证之和。验证器 `0x61` 预像长为有序输出字节加每个输入 41 字节和固定 49 字节。若四个持币输入也都用完整 `0x61`，4→4 模型增至 47,547 字节，每个持币输入携带同一份当前输出。固定形状的目标仍为 0 B/代。

专用单槽和四槽递归构件分别编译为 4,640,991 和 14,319,989 条约束，均包含密钥认证与 BSB22 递归验签。共用同一四槽电路时，1→4 只激活一个父槽，但仍承担该电路已实例化的填充槽成本。用实际 8,068 字节原生铸造父估算私有 SHA256d，单槽加一个父哈希约 916 万条，四槽逐个开四份相同大小的父约 3,238 万条，均未计入其他当前交易规则。真实出证及节点执行成本另行记录。 [紧凑铸造大小](../fixtures/v2-bounded-native-mint-regtest-summary.json)

用小型父交易与真实 BSB22 测试证明组合求解后，专用 1→4 为 5,790,214 条约束，专用 4→4 为 17,092,424 条。两者把实际父 vout 的代币数量交给同一守恒函数，重建前序证明摘要，并承诺实际全部四个输出。改量后重算本笔公开声明也会被拒绝。组合测试的前序证明属于测试电路，发行基例、外层新参数、签名验收及连续入块仍待完成。 [组合测试](../recursion/continuity/wire_transfer_test.go)

独立 BSV Node 已确认 1→4 和 4→4 的 Chronicle 声明边界测试，Script 从本笔实际预像和 77 字节回执重建两个公开量，再用节点验签绑定该预像。错误回执数量和改后的实际输出配旧预像均被拒绝。节点夹具直接核对公开量，完整交易验收仍需外层 Groth16 和持币锁。 [声明边界节点记录](../fixtures/v2-committed-transfer-context-regtest-summary.json)

守恒按 Token 最小单位与 satoshi 分别核对。1→4 的四个 Token 输出必须各有正数最小单位。保留本试验的聪数守恒时，一个 4,000 satoshi 的代币输入可分给四个各 1,000 satoshi 的输出。若策略要求四个输出各 1,000 satoshi，且原代币输入只有 1,000 satoshi，补足载体聪数需要明确的独立资金规则。
